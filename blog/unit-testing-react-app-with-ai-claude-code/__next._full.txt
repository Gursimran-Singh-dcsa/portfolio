I used Claude Code to take it from zero to <strong>1,676 tests across 98 test files</strong>, with every coverage metric above 80% and <strong>no application source code changed</strong> to make a test pass.</p>
<p>This post is how that went: the plan, the setup, the mistake I had to revert, the rules that kept the AI honest, and what I would not trust it with. For confidentiality I can&#39;t name the customer or the product, and every example here is generic.</p>
<h2>The starting point</h2>
<p>The application was a multi-step web application with several flows: an organic one, a few partner-referred ones, a sub-flow, and standalone links. It had been built and maintained for a while, and every change was verified the old way: by clicking through it.</p>
<p>The ask was simple to say and hard to do:</p>
<ul>
<li>Real unit tests with React Testing Library, written at the level of what a user sees and does.</li>
<li>Every API response mocked, so tests never depend on a real backend.</li>
<li>Maximum branch and statement coverage.</li>
<li>A plan first, written down as documents and a specialised agent, not an unplanned prompt marathon.</li>
</ul>
<h2>How the work went</h2>
<p>I split it into five stages.</p>
<ol>
<li><strong>Plan.</strong> A testing strategy and a test-writing guide, plus a <code>unit-test-writer</code> agent that knows this repository.</li>
<li><strong>Setup.</strong> Vitest, MSW, fixtures, render helpers and a network guard.</li>
<li><strong>Screens.</strong> One screen at a time, in flow order, with me choosing the next one.</li>
<li><strong>Coverage.</strong> Push every metric past 80%, then ratchet the thresholds.</li>
<li><strong>Stabilise.</strong> Find and fix flaky tests by running suites under load.</li>
</ol>
<h3>The course correction</h3>
<p>The AI&#39;s first pass was not what I wanted. It started testing helper functions in isolation, which is fast and looks productive, and it produces a lot of green tests that say little about whether a screen works.</p>
<p>I reverted it and switched to <strong>screen-by-screen tests</strong>: render a real screen, type and click like a user, and assert on what appears. That is where the real value was, and it is where the bugs were found. If you take one thing from this post, it is to check early whether the AI is testing the right level.</p>

<h2>No test can reach a real API</h2>
<p>This was the most important rule, because the application talks to real services. I made it hard to break with three layers:</p>
<ol>
<li><strong>Fake hosts.</strong> Every environment URL is pinned to a <code>*.test.local</code> host, so real environment files are never read.</li>
<li><strong>MSW answers everything.</strong> Each test declares the responses it needs: success, a 500, or a network error.</li>
<li><strong>A network guard.</strong> It blocks every real TCP connection and DNS lookup, and any attempt fails the test.</li>
</ol>
<p>Why a third layer? MSW&#39;s &quot;error on unhandled request&quot; option still let a request escape to the network in this setup. So I added the guard, and wrote a test that proves the guard itself works.</p>
<h2>How AI was used</h2>
<p>Using AI well here was mostly about structure, not prompting.</p>
<ul>
<li><strong>Docs as the contract.</strong> A strategy document and a test-writing guide set the rules once. The project&#39;s <code>CLAUDE.md</code> points every session at them, so a new session starts with the same rules.</li>
<li><strong>A specialised agent.</strong> <code>unit-test-writer</code> knows the helpers, the data rules and the conventions of this repository, so it does not invent its own style each time.</li>
<li><strong>Parallel agents.</strong> For the coverage push I split the work across agents by area, each briefed narrowly.</li>
<li><strong>Me in the loop.</strong> I picked each screen, set the rules, reviewed the results and reverted what was wrong.</li>
</ul>
<h2>Keeping the AI honest</h2>
<p>Tests written by an AI can be green and worthless. These are the checks I used to make sure they are not.</p>
<ul>
<li><strong>Mutation checks.</strong> Break one line of application code on purpose; the matching test must fail. Then restore it.</li>
<li><strong>Never edit the app to pass a test.</strong> No application source was changed, and I checked it with <code>git diff</code>.</li>
<li><strong>Pin bugs, don&#39;t hide them.</strong> When the app behaves wrongly, the test records it as &quot;current behaviour&quot; and the bug is logged as a finding, instead of being quietly worked around.</li>
<li><strong>Synthetic data only.</strong> Phone numbers in the 555-01xx range, <code>@example.com</code> emails, an SSN area of 000 and published test card numbers. No real customer data went anywhere near a prompt or a test.</li>
<li><strong>Stress runs.</strong> Run two or three suites in parallel to flush out flaky, timing-dependent tests.</li>
<li><strong>Ratcheted thresholds.</strong> Coverage minimums only go up, so gains cannot quietly slip back.</li>
</ul>

<h2>Who did what</h2>
<p><strong>The AI</strong> wrote the setup, helpers and tests, read every branch of each screen, diagnosed silent failures and flakiness, ran the mutation checks and stress runs, and logged every bug it pinned.</p>
<p><strong>I</strong> set the goal and the hard rules, chose the screen-by-screen approach, reverted work that went the wrong way, reported flaky runs from my own machine, and decided what ships and what to fix.</p>
<h3>Limits to know</h3>
<ul>
<li>Not every test was mutation-checked, only a sample.</li>
<li>Tests that pin today&#39;s bugs pass while the app is wrong. They will flip when the bug is fixed, which is the point, but it means a green suite does not mean a bug-free app.</li>
<li>The coverage number measures what the tests execute, not whether the assertions are good. That is why the mutation checks matter.</li>
</ul>

</ol>
<h2>FAQ</h2>
<h3>Can AI write unit tests for an existing React app?</h3>
<p>Yes, but only with structure. Written rules, a repository-aware agent, mocked network calls and a human choosing what to test took this app from zero to 1,676 tests. Prompting alone would not have.</p>
<h3>Which tools did you use for React unit testing?</h3>
<p>Vitest with jsdom as the runner, React Testing Library and user-event for user-level tests, MSW to mock every API response, and coverage-v8 for coverage with ratcheting thresholds.</p>
<h3>How do you know AI-written tests are actually good?</h3>
<p>I broke a line of application code on purpose and confirmed the matching test failed, kept the application source untouched, and pinned wrong behaviour as findings instead of hiding it. I only did this for a sample of tests, not all of them.</p>
<h3>How do you stop tests from calling a real API?</h3>
<p>Use three layers: fake hosts, MSW answering every request, and a network guard that fails any real connection.</p>
